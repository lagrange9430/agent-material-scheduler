# 05 复盘：最难的问题、学到什么、下一步

## 1. 三个最难的问题

### 1.1 "怎么证明这不是固定脚本"

这道题最大的坑不是写不出流程，而是**写出来的东西恰好也能跑通所有用例，但模型其实没在做决策**。串行调用四个工具、用 if 判断结果，用例照样全绿。

我先试过用"两条执行路径"来证明——不够。两条路径可以是写死的两个分支。

真正有用的做法是**受控对照**：同一输入、同一份数据、同一套代码，只改排期表里一个字段，动作序列必须变化。于是有了 `a2-conflict` 与 `c1-control-free`：

- 18:00 被占 → 查时段 → 保存 19:00 → **请求确认**
- 18:00 空闲 → 查时段 → 保存 18:00 → **直接完成**

评审改一个 JSON 字段就能复现这个差异。这比任何文字解释都硬。

### 1.2 "待确认"和"已保存"怎么共存

最初我把这两件事当成互斥的：要么存草稿，要么等确认。结果参考实例里那句"标记待确认"和"重复保存只产生一份草稿"打架了——如果没保存，哪来的重复保存？

想通之后的设计是：**草稿可以存在，但它的状态是"待确认"**。于是有了三层边界：

1. 数据层同时存 `requested_slot` 和 `proposed_slot`，不等就必须写 `deviation`；
2. 语义层 `needs_user_confirmation=true` 时，任务状态不可能是 `completed`；
3. 重放层用 `--approve` 把"用户同意"变成输入，让确认后的路径也能离线复现。

第三层是补上去的。没有它，"未经同意不改期"只能靠人相信，测试根本断言不了。

### 1.3 幂等与"用户确认"的冲突

第三层刚加上就撞车了：带 `--approve` 重跑同一个请求，幂等键相同，工具直接返回 `duplicate`，草稿还停在待确认。

这里有个真正的设计分叉：

- 换个幂等键（把"是否确认"算进 key）→ 会产生两份草稿，违反"同一请求只有一份"；
- 保持幂等键、但允许就地更新 → 一份草稿，`revision` 从 1 变 2。

选了后者，并补了一条规则：**已确认的草稿不允许被后续请求降级回待确认**。否则一个手滑的重跑就能把用户刚确认的排期打回去。

## 2. 学到了什么

1. **"能跑通"和"是对的"是两件事**。第 3 个错误（幻觉进结论）发生时，40 个测试全绿——因为测试断言的是结构，不是语义。后来我把结论改成由事实拼装，才让幻觉无处可藏。
2. **验收标准要能写成断言**。凡是写成"模型应该合理判断"的，都没法测；写成"草稿数必须等于 1""`draft_id` 必须为 null"的，才能测。
3. **边界要先于实现确定**。花时间在需求上（哪些必做、哪些明确不做、状态枚举穷举）比多写 200 行代码省事得多——`draft_status` 少一个 `updated`，后面就要绕一圈。
4. **外部依赖必须先探测**。模型名是用户给的，但账户不支持；如果先写完 500 行再发现，返工成本高得多。

## 3. 如果还有时间，我会做什么

| 优先级 | 事项 | 为什么 |
|---|---|---|
| P0 | 用 SQLite 替换 `drafts.json`，加事务 | 现在多进程并发写会丢更新，"防重复"在并发下不成立 |

| P2 | 把 `--approve` 换成真实审批回调 | 现在只是模拟用户已同意 |

## 5. 一句话总结

这道题真正考的不是"能不能调通模型"，而是**能不能证明模型在做决定、且决定没有越界**。我的做法是把这两件事都变成可执行、可复现、可断言的东西：对照实验证明前者，三层确认边界和硬约束护栏证明后者。
